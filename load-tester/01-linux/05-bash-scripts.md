## Зачем это нужно

Команды из прошлых уроков ты набирал руками. Один раз это нормально, но в работе проверку нужно повторять: перед каждым тестом убедиться, что стенд жив, после каждого изменения проверить, что ничего не сломалось, ночью запустить ту же проверку по расписанию. Руками это долго, скучно и каждый раз чуть по-разному: сегодня забыл один адрес, завтра другой. **Скрипт** (script) это текстовый файл с командами, которые выполняются одна за другой по одному запуску. Он делает проверку одинаково каждый раз и умеет сказать «всё хорошо» или «плохо» не только тебе, но и другим программам.

Шаг проекта: ты напишешь скрипт `~/perf-lab/scripts/check-stand.sh`, который проверяет стенд «Магазин»: слушает ли порт, отвечают ли основные адреса нужными кодами, не слишком ли медленно. Этот скрипт ты будешь запускать перед каждым нагрузочным тестом до конца курса, а в [теме 6](../06-api-testing/index.md) его запустит автоматическая проверка.

## Картина целиком

Возьми памятку дежурного охранника: «обойди здание, проверь, что дверь А закрыта, дверь Б закрыта, свет горит. Если что-то не так, запиши, где именно, и позвони. Если всё в порядке, ничего не звони». Охранник не думает над порядком, он идёт по списку. Скрипт это такая памятка, которую выполняет компьютер: **последовательность** шагов, **условия** («если дверь открыта...»), **повторы** («для каждой двери из списка») и **итог** («позвони или не звони»).

```mermaid
flowchart TD
    A["Запуск скрипта<br/>./check-stand.sh"] --> B["Взять хост и порт<br/>из аргументов"]
    B --> C{"Порт слушает?"}
    C -->|нет| D["Сообщить и выйти<br/>с кодом 2"]
    C -->|да| E["Для каждого адреса:<br/>curl и сверка кода"]
    E --> F{"Были сбои?"}
    F -->|нет| G["Выход с кодом 0"]
    F -->|да| H["Выход с кодом 1"]
```

У скрипта есть ранний выход (порт закрыт, дальше идти нет смысла), цикл по проверкам и итог в виде числа. Это число (**код возврата**, дальше о нём подробно) и есть способ, которым скрипт «говорит» с другими программами: `0` означает «успех», любое другое «неудача».

## Теория

### Скрипт: файл, который можно запустить

**Зачем это существует.** Набранные в терминале команды исчезают, когда закрываешь окно. Если сохранить их в файл, их можно выполнять сколько угодно раз.

**Аналогия.** Рецепт, записанный на карточку: не нужно каждый раз вспоминать порядок действий.

**Как это устроено.** Скрипт это обычный текстовый файл. Чтобы система знала, чем его выполнять, первой строкой пишут **шебанг** (shebang): символы `#!` и путь к интерпретатору:

```bash
#!/usr/bin/env bash
echo "Привет из скрипта"
```

`#!/usr/bin/env bash` значит «запусти этот файл программой `bash`, найдя её в системе». Остальные строки это команды. Всё после `#` это **комментарий**: пояснение для человека, которое Bash пропускает. Чтобы файл можно было запускать, ему нужно право на исполнение:

```bash
chmod +x hello.sh
./hello.sh
```

`chmod +x` добавляет право «исполнять». `./hello.sh` запуск: `./` означает «из текущего каталога» (простое `hello.sh` оболочка искала бы в системных каталогах из `PATH`, как ты видел в [уроке 1.1](01-workstation-terminal.md), и не нашла бы). Запустить без права на исполнение тоже можно: `bash hello.sh`.

**Что путают.** `./hello.sh` и `hello.sh`; забытое `chmod +x` (ошибка `Permission denied`); комментарий `#` и шебанг `#!`: шебанг только в самой первой строке.

> **Проверь понимание:** ты написал `check.sh` и запускаешь его командой `check.sh`, получаешь `command not found`. Что не так?

<details markdown="1">
<summary>Ответ</summary>

Оболочка ищет команды только в каталогах из `PATH`, а текущего каталога там нет. Нужно указать путь явно: `./check.sh`. Если после этого будет `Permission denied`, не хватает права исполнения: `chmod +x check.sh`.

</details>

### Переменные и кавычки

**Зачем это существует.** Адрес сервера, порт, допустимое время ответа встречаются в скрипте много раз. Если вписывать их везде, при смене порта придётся править десять мест. Переменная (variable) это имя, под которым хранится значение: поменял в одном месте и поменялось везде.

**Аналогия.** Подписанная банка на полке: ты не повторяешь «пшено», а берёшь банку с этикеткой «крупа». Поменял содержимое, все рецепты используют новое.

**Как это устроено.**

```bash
HOST="127.0.0.1"
PORT=8000
echo "Проверяю $HOST:$PORT"
```

```text
Проверяю 127.0.0.1:8000
```

Три правила, на которых ломаются новички:

1. **Вокруг `=` нет пробелов.** `PORT=8000` правильно, `PORT = 8000` ошибка: Bash решит, что `PORT` это команда.
2. **Читают значение со знаком доллара:** `$PORT` или `${PORT}` (фигурные скобки нужны, когда рядом буквы: `${HOST}_log`).
3. **Кавычки.** Двойные `"..."` подставляют значения переменных, одинарные `'...'` печатают всё буквально:

```bash
NAME="стенд"
echo "Проверяю $NAME"
echo 'Проверяю $NAME'
```

```text
Проверяю стенд
Проверяю $NAME
```

Значения с пробелами и переменные почти всегда берут в двойные кавычки: `"$URL"`, иначе значение с пробелом развалится на два слова.

**Подстановка команды** `$(...)` запускает команду и подставляет её вывод:

```bash
TODAY=$(date +%F)
COUNT=$(wc -l < access.log)
echo "На $TODAY в логе $COUNT строк"
```

```text
На 2026-10-03 в логе 10000 строк
```

`date +%F` печатает дату в виде `2026-10-03`; `wc -l < access.log` считает строки в файле (`<` подаёт файл на вход команде, как `|` подаёт вывод другой команды). Скрипт сохранил результат и использует его дальше.

**Аргументы скрипта.** Всё, что ты написал после имени, попадает в специальные переменные: первое слово в `$1`, второе в `$2`, и так далее. Чтобы задать значение по умолчанию, пишут `${1:-значение}`: «возьми `$1`, а если он пустой, бери вот это».

```bash
HOST="${1:-127.0.0.1}"
PORT="${2:-8000}"
```

Тогда `./check-stand.sh` проверит `127.0.0.1:8000`, а `./check-stand.sh shop.lab 9000` другой хост и порт, без правки файла.

**Разобранный пример.**

```bash
#!/usr/bin/env bash
HOST="${1:-127.0.0.1}"
PORT="${2:-8000}"
BASE_URL="http://$HOST:$PORT"
echo "Проверяю $BASE_URL"
```

Запуск без аргументов печатает `Проверяю http://127.0.0.1:8000`, запуск с `./script.sh example.com 80` печатает `Проверяю http://example.com:80`. Одна запись адреса собирается из двух переменных, а все дальнейшие команды используют `$BASE_URL`.

**Что путают.** Пробелы вокруг `=`; одинарные кавычки там, где нужна подстановка; значение без кавычек, когда в нём пробелы; `$(...)` и просто круглые скобки.

> **Проверь понимание:** что напечатает `X=5; echo 'значение $X'; echo "значение $X"`?

<details markdown="1">
<summary>Ответ</summary>

`значение $X` и `значение 5`. Одинарные кавычки не подставляют переменную, двойные подставляют.

</details>

### Код возврата: как скрипт и команды говорят «успех» или «ошибка»

**Зачем это существует.** Глазами смотреть на вывод скрипта можно, пока ты рядом. Но если скрипт запускает другая программа (автопроверка, расписание), ей нужен ответ, который она может проверить сама: «получилось» или «нет». Для этого каждая команда после завершения возвращает число.

**Как это устроено.** **Код возврата** (exit code, exit status) это число от 0 до 255, которое команда отдаёт при завершении. Договорённость такая: **`0` значит успех, любое другое значение значит ошибку** (какое именно, решает автор программы). Последний код лежит в специальной переменной `$?`:

```bash
ls /tmp
echo "код: $?"
ls /нет-такого-каталога
echo "код: $?"
```

```text
(список файлов)
код: 0
ls: cannot access '/нет-такого-каталога': No such file or directory
код: 2
```

Поэтому `curl` на закрытом порту завершается с кодом 7, как ты видел в [уроке 1.4](04-network-cli.md) (там это был номер ошибки в тексте `curl: (7)`, и он же код выхода). Свой скрипт завершается командой `exit N`: `exit 0` успех, `exit 1` сбой, `exit 2` другая причина (мы возьмём 2 для «порт закрыт»). Если в конце нет `exit`, код равен коду последней выполненной команды.

Код возврата проверяют условием (следующий раздел) или связками:

| Запись | Что значит |
|---|---|
| `команда1 && команда2` | выполнить вторую, только если первая успешна |
| `команда1 \|\| команда2` | выполнить вторую, только если первая провалилась |
| `команда1 ; команда2` | выполнить вторую в любом случае |

```bash
mkdir -p ~/perf-lab/scripts && echo "каталог готов"
curl -sf http://127.0.0.1:8000/healthz > /dev/null || echo "стенд не отвечает"
```

В первой строке слово «каталог готов» печатается, только если `mkdir` отработал успешно. Во второй сообщение о неудаче печатается, только если `curl` вернул ненулевой код (флаг `-f` из прошлого урока заставляет `curl` считать ответы 4xx и 5xx ошибкой).

```mermaid
flowchart TD
    A["Команда выполнена"] --> B{"Код возврата"}
    B -->|"0"| C["Успех:<br/>идём дальше"]
    B -->|"не 0"| D["Ошибка:<br/>реагируем или выходим"]
```

К любой команде достаточно одного вопроса: «ноль или не ноль». Поэтому кодом возврата легко пользоваться всем: скриптам, автоматическим проверкам и инструментам непрерывной интеграции.

**Что путают.**

- Код возврата `0` это успех, а не «ничего»: в Bash «ноль значит хорошо», в большинстве языков программирования ноль значит «ложь», и это путает.
- `$?` меняется после каждой команды, даже после `echo`. Нужное значение сохраняй сразу: `rc=$?`.
- `curl` без `-f` вернёт `0` даже при ответе 500: он «успешно получил ответ». Проверять нужно либо `-f`, либо сам HTTP-код.

> **Проверь понимание:** скрипт делает `curl -s http://127.0.0.1:8000/readyz`, сервис отвечает `503`. Какой код возврата у `curl` и почему это ловушка?

<details markdown="1">
<summary>Ответ</summary>

`0`: `curl` без `-f` считает успехом то, что ответ получен, и не смотрит на код 503. Проверка `if curl ...; then echo OK` напечатает «OK» для неработающего сервиса. Нужно добавить `-f` или сравнивать `%{http_code}` с ожидаемым значением.

</details>

### Условия: if

**Зачем это существует.** Скрипт должен принимать решения: если порт закрыт, прекратить, если ответ медленный, отметить.

**Как это устроено.** Основная форма:

```bash
if [ "$code" = "200" ]; then
  echo "OK"
else
  echo "FAIL"
fi
```

`if` проверяет код возврата команды после него. Команда `[ ... ]` (это настоящая команда, ещё её называют `test`) проверяет условие и возвращает `0`, если оно истинно. Поэтому внутри скобок **пробелы обязательны**: `[ "$code" = "200" ]`, а не `["$code"="200"]`. Блок `then ... else ... fi` (слово `if` задом наперёд закрывает условие). Вариант с несколькими ветками: `elif`.

Сравнения бывают двух видов, и путать их нельзя:

| Что сравниваем | Запись | Пример |
|---|---|---|
| Строки | `=`, `!=` | `[ "$code" = "200" ]` |
| Числа | `-eq` (равно), `-ne` (не равно), `-gt` (больше), `-lt` (меньше), `-ge`, `-le` | `[ "$ms" -gt 500 ]` |
| Файл существует | `-f файл`, `-d каталог` | `[ -f access.log ]` |
| Строка пустая | `-z "$x"` | `[ -z "$HOST" ]` |

Знаки `>` и `<` внутри `[ ]` **не сравнивают числа**: они работают как перенаправление и создают файл с именем «500». Для чисел используй только `-gt`, `-lt` и остальные.

Условием может быть и сама команда: «если команда успешна»:

```bash
if curl -sf --max-time 3 http://127.0.0.1:8000/healthz > /dev/null; then
  echo "стенд жив"
else
  echo "стенд не отвечает"
fi
```

**Разобранный пример.** Классифицируем время ответа:

```bash
ms=620
if [ "$ms" -gt 1000 ]; then
  echo "очень медленно"
elif [ "$ms" -gt 500 ]; then
  echo "медленно"
else
  echo "нормально"
fi
```

```text
медленно
```

620 не больше 1000, поэтому первая ветка пропущена; 620 больше 500, и срабатывает вторая. Ветки проверяются сверху вниз, срабатывает первая подходящая.

**Что путают.** `=` и `-eq` (строки и числа); забытые пробелы внутри `[ ]`; `>` вместо `-gt`; забытое `fi`.

> **Проверь понимание:** что не так в `if [ $ms > 500 ]; then`?

<details markdown="1">
<summary>Ответ</summary>

Знак `>` внутри `[ ]` это перенаправление вывода в файл «500», а не сравнение. Условие почти всегда окажется «истинным» и создаст лишний файл. Правильно: `if [ "$ms" -gt 500 ]; then`.

</details>

### Циклы: for и while

**Зачем это существует.** Проверить нужно не один адрес, а пять. Писать пять одинаковых блоков значит пять раз копировать, и пять раз ошибаться. Цикл (loop) повторяет блок команд для каждого значения.

**Как это устроено.** Цикл `for` перебирает список значений:

```bash
for path in /healthz /readyz /api/categories; do
  echo "Проверяю $path"
done
```

```text
Проверяю /healthz
Проверяю /readyz
Проверяю /api/categories
```

`for имя in список; do ... done`: на каждом шаге переменная `path` получает следующее значение, тело между `do` и `done` выполняется. Диапазон чисел записывают как `{1..5}`, и ты уже использовал такой цикл в [уроке 1.3](03-processes-resources.md): `for i in {1..4}; do yes > /dev/null & done`.

Цикл `while` повторяется, пока условие истинно. Типичное применение: проверять стенд раз в секунду, пока он не поднимется (`!` перед командой значит «пока команда **не** успешна»):

```bash
while ! curl -sf http://127.0.0.1:8000/healthz > /dev/null; do
  echo "жду стенд..."
  sleep 1
done
echo "стенд поднялся"
```

`sleep 1` пауза одна секунда. Есть и обратный цикл `until` («повторять, пока условие не выполнится»), но с `while !` читать проще. Так скрипт ждёт запуска сервиса и только потом идёт дальше. Такая конструкция понадобится с [урока 2.1](../02-web/01-client-server-http.md): стенд поднимается десятки секунд, и тест нельзя запускать раньше.

**Разобранный пример.** Повторить проверку несколько раз и посчитать неудачи:

```bash
failed=0
for i in 1 2 3; do
  if ! curl -sf --max-time 2 http://127.0.0.1:8000/healthz > /dev/null; then
    failed=$((failed + 1))
  fi
  sleep 1
done
echo "неудач: $failed из 3"
```

`!` перед командой меняет смысл на обратный: «если команда **не** успешна». `$((failed + 1))` это арифметика: Bash считает выражение внутри двойных скобок. Результат `неудач: 0 из 3`, если стенд жив. Счётчик, который растёт внутри цикла, это стандартный приём: в конце по нему решают, считать ли проверку проваленной.

**Что путают.** Забытые `do` и `done`; арифметику пишут `$((a + 1))`, а не `$a + 1`; бесконечный `while true` без `sleep` нагружает процессор на 100% (как `yes` из урока 1.3): всегда добавляй паузу и условие выхода.

> **Проверь понимание:** скрипт ждёт стенд циклом `while ! curl ...; do sleep 1; done`, но стенд так и не поднимается. Чем это опасно и как исправить?

<details markdown="1">
<summary>Ответ</summary>

Скрипт зависнет навсегда: цикл без ограничения числа попыток. Исправление: считать попытки и выходить после предела, например `for i in {1..30}; do curl ... && break; sleep 1; done`, а после цикла проверять, успешно ли закончили.

</details>

### Функции: один раз написал, много раз вызвал

**Зачем это существует.** Проверка одного адреса состоит из нескольких команд. Если вставлять их пять раз, скрипт раздувается, а исправление ошибки приходится делать пять раз. **Функция** (function) это блок команд с именем, который вызывают как команду.

**Как это устроено.**

```bash
greet() {
  local name="$1"
  echo "Привет, $name"
}
greet "стенд"
greet "команда"
```

```text
Привет, стенд
Привет, команда
```

Внутри функции аргументы приходят в `$1`, `$2` так же, как у скрипта. `local` делает переменную видимой только внутри функции (без неё переменная стала бы общей на весь скрипт, и функции начали бы мешать друг другу). Вывод функции можно перехватить `$(greet "x")`, а её код возврата проверить через `$?` или `if`. Определять функцию нужно **до** первого вызова.

**Что путают.** Функцию определили, но не вызвали (она сама ничего не делает); не написали `local`; вызывают функцию со скобками `greet()` (скобки нужны только при определении).

> **Проверь понимание:** функция внутри меняет переменную `count` без `local`, и после вызова значение в основной части скрипта тоже изменилось. Это ошибка?

<details markdown="1">
<summary>Ответ</summary>

Зависит от замысла. Без `local` переменная общая на весь скрипт, и так это работает (мы используем это для счётчика сбоев `failed` в основном скрипте). Но для вспомогательных переменных вроде `code` и `ms` нужен `local`: иначе значения одной проверки случайно просачиваются в другую.

</details>

### Как Bash выполняет скрипт

**Как это устроено.** Bash читает файл сверху вниз по одной команде. Если команда не удалась, он **по умолчанию идёт дальше**, а не останавливается: скрипт без проверок может пройти до конца и выдать «успех» при сломанной середине. Пошаговый ход нашего скрипта проверки:

Порядок такой: сначала подготовка (аргументы), потом ранняя остановка при явной поломке, затем повторяемая часть (функция) и в конце итог. Так устроено большинство рабочих скриптов проверки.

**Про строгий режим.** В начало рабочих скриптов часто пишут `set -euo pipefail`: «останавливайся при первой ошибке, ругайся на необъявленные переменные». Это полезно, но у новичка даёт неожиданные остановки (например, `grep` без совпадений возвращает `1` и скрипт прерывается). В учебном `check-stand.sh` мы его не берём: нам нужно собрать **все** сбои проверки, а не остановиться на первом, поэтому счётчик `failed` и итоговый `exit` пишем вручную. В рабочих скриптах, где нужно остановиться на первой ошибке, пиши эту строку сразу: она спасает от тихих сбоев.

**Проверка скрипта.** Установленная в этом уроке утилита `shellcheck` читает скрипт и подсказывает типичные ошибки (забытые кавычки, лишние пробелы): `sudo apt install -y shellcheck`, затем `shellcheck скрипт.sh`. Полезная привычка: запускать её перед первым запуском.

### 4. Итоговый скрипт: проверка стенда

Теперь соберём всё вместе: порт, функция, счётчик, медленные ответы, код выхода.

```bash
nano ~/perf-lab/scripts/check-stand.sh
```

```bash
#!/usr/bin/env bash
# check-stand.sh: быстрая проверка стенда «Магазин».
# Запуск: ./check-stand.sh [хост] [порт]   (по умолчанию 127.0.0.1 8000)
# Код выхода: 0 всё в порядке, 1 есть сбои, 2 порт закрыт.

HOST="${1:-127.0.0.1}"
PORT="${2:-8000}"
BASE_URL="http://$HOST:$PORT"
MAX_TIME=3      # дольше этого запрос считается зависшим, секунд
SLOW_MS=500     # медленнее этого помечаем SLOW, миллисекунд
failed=0

# Шаг 1. Порт слушают?
if ! (exec 3<>"/dev/tcp/$HOST/$PORT") 2>/dev/null; then
  echo "FAIL порт $PORT на $HOST закрыт: сервис не запущен?"
  exit 2
fi
echo "OK   порт $PORT открыт"

# check_url ПУТЬ ОЖИДАЕМЫЙ_КОД: один запрос, печатает строку результата.
check_url() {
  local path="$1" expected="$2"
  local out code secs ms mark
  out=$(curl -s -o /dev/null --max-time "$MAX_TIME" \
        -w '%{http_code} %{time_total}' "$BASE_URL$path")
  code="${out%% *}"
  secs="${out##* }"
  ms=$(awk -v s="$secs" 'BEGIN { printf "%d", s * 1000 }')

  if [ "$code" != "$expected" ]; then
    mark="FAIL"
    failed=$((failed + 1))
  elif [ "$ms" -gt "$SLOW_MS" ]; then
    mark="SLOW"
  else
    mark="OK  "
  fi
  printf '%s %-24s код %s (ждали %s) за %s мс\n' "$mark" "$path" "$code" "$expected" "$ms"
}

# Шаг 2. Проверяем адреса: путь и ожидаемый код.
check_url /healthz 200
check_url /readyz 200
check_url /api/categories 200
check_url "/api/products?size=5" 200
check_url /api/products/999999 404

# Шаг 3. Итог.
if [ "$failed" -eq 0 ]; then
  echo "Итог: всё в порядке"
  exit 0
fi
echo "Итог: сбоев $failed"
exit 1
```

Разбор незнакомых мест (две первые подстановки сложные: достаточно понять, что они делают, запоминать их не нужно):

- `(exec 3<>"/dev/tcp/$HOST/$PORT")` Bash умеет сам открывать TCP-соединение: специальный «файл» `/dev/tcp/хост/порт` соединяется с портом, и код возврата говорит, получилось ли. `2>/dev/null` прячет сообщение об ошибке. Открывать соединение скобками `( ... )` нужно, чтобы оно закрылось, когда скобки закончатся. Если порт закрыт, команда вернёт ненулевой код, и `if !` сработает.
- `"${out%% *}"` и `"${out##* }"`: из строки вида `200 0.003412` берут первое слово (до первого пробела: `%%`) и последнее (после последнего пробела: `##`). Это способ разрезать строку без `awk`. Если не поймёшь с первого раза, не страшно: скопируй как есть.
- `awk -v s="$secs" 'BEGIN { printf "%d", s * 1000 }'` умножает секунды на 1000 и печатает целое число: Bash сам не считает дробные числа, поэтому арифметику с `0.003412` отдаём `awk`. `-v s=...` передаёт значение в `awk`.
- `printf '%s %-24s ...'` форматированный вывод: `%s` подставляет строку, `%-24s` строка шириной 24 символа, выровненная влево (чтобы колонки были ровными).
- `\` в конце строки значит «команда продолжается на следующей строке».

```bash

~/perf-lab/scripts/check-stand.sh; echo "код выхода: $?"
```

```text

OK   /healthz                 код 200 (ждали 200) за 5 мс
OK   /readyz                  код 200 (ждали 200) за 1 мс

Пятая строка показывает важную идею: ожидаемый код не всегда 200. Запрос несуществующего товара **должен** вернуть 404, и если вдруг вернёт 200, это ошибка. Последняя строка `код выхода: 0` значит «всё хорошо» для любой программы, которая запустит скрипт. Время ответов можно оценить на графике: именно такие числа выдаёт скрипт на реальном стенде при спокойной работе.

- `./check-stand.sh: line 12: syntax error near unexpected token 'then'`: забыт `;` перед `then` или пробел внутри `[ ]`. Номер строки в сообщении точный: смотри на неё и на предыдущую.

## Сломай и почини

**Поломка.** Коллега написал упрощённую версию проверки и говорит, что она «работает». Создай её:

```bash
cat > ~/perf-lab/scripts/check-bad.sh <<'TXT'
#!/usr/bin/env bash
if curl -s http://127.0.0.1:8000/api/products/999999 > /dev/null; then
  echo "OK стенд работает"
else
  echo "FAIL"
fi
TXT
chmod +x ~/perf-lab/scripts/check-bad.sh
~/perf-lab/scripts/check-bad.sh
```

Скрипт напечатает `OK стенд работает`, хотя адрес `/api/products/999999` на самом деле возвращает `404`. Потом останови сервер (`Ctrl+C` в первом терминале) и запусти ещё раз.

**Задача.** Найди, почему скрипт врёт в первом случае, и почини его так, чтобы он честно сообщал об ошибке в обоих.

<details markdown="1">
<summary>Разбор</summary>

1. Причина: `curl` без `-f` возвращает код `0` всегда, когда получил **какой-то** ответ, включая 404 и 500. Условие `if curl ...` проверяет только код возврата `curl`, поэтому для 404 оно истинно, и скрипт печатает «OK». Это та самая ловушка из раздела про код возврата.
2. После остановки сервера `curl` не сможет соединиться и вернёт код 7: скрипт напечатает `FAIL`. Значит, скрипт ловит **только** сетевые сбои и пропускает ошибки приложения.
3. Исправление, вариант 1: добавить `-f`: `curl -sf --max-time 3 ...`. Тогда код 404 и 500 тоже дают ненулевой код возврата. Вариант 2 лучше: брать HTTP-код через `-w '%{http_code}'` и сравнивать с ожидаемым, как в `check-stand.sh`. Он различает «404 ожидаем» и «404 неожиданный» и показывает сам код, а не просто «FAIL».
4. Добавь ещё `--max-time`: без него `curl` может ждать бесконечно, и скрипт зависнет вместо того чтобы сообщить о сбое.
5. Проверка: запусти исправленный скрипт при работающем сервере (ожидаемо `FAIL` для 404 с `-f`, если ждёшь 200), потом при остановленном, и сравни коды выхода командой `echo $?`.

Вывод: в скриптах проверка «команда выполнилась» и «сервис здоров» это разные вещи. Скрипт, который проверяет только первое, даёт ложное чувство безопасности, а ложное «всё хорошо» перед нагрузочным тестом хуже честного «не работает».

</details>

Убери за собой: останови сервер (`Ctrl+C`), удали учебные файлы. Скрипт `check-stand.sh` останется, он пригодится дальше.

```bash

rm ~/perf-lab/scripts/check-bad.sh ~/perf-lab/scripts/hello.sh ~/perf-lab/scripts/mini-check.sh
ls ~/perf-lab/scripts
```

## Словарик урока

| Термин | Простыми словами |
|---|---|
| Скрипт (script) | Текстовый файл с командами, которые выполняются одна за другой по одному запуску |
| Шебанг (shebang) | Первая строка `#!/usr/bin/env bash`: какой программой запускать файл |
| Комментарий | Строка после `#`: пояснение для человека, Bash её пропускает |
| Переменная | Имя, под которым хранится значение: `PORT=8000`, читается как `$PORT` |
| Аргумент скрипта | Слово после имени скрипта: первое лежит в `$1`, второе в `$2` |
| `${1:-значение}` | «Возьми первый аргумент, а если его нет, возьми значение» |
| Подстановка команды `$(...)` | Запустить команду и подставить её вывод на это место |
| Код возврата (exit code) | Число, которое команда отдаёт при завершении: 0 успех, другое ошибка |
| `$?` | Код возврата последней команды |
| `exit N` | Завершить скрипт с кодом N |
| `&&`, `\|\|` | «Если успешно, то...» и «если провалилось, то...» |
| `if ... then ... fi` | Условие: выполнить блок, если проверка успешна |
| `[ ... ]` | Команда проверки условия: пробелы внутри обязательны |
| `-eq`, `-gt`, `-lt` | Сравнение чисел (равно, больше, меньше); для строк `=` |
| Цикл (loop) | Повтор блока команд: `for` по списку, `while` по условию |
| Функция | Блок команд с именем, который вызывают как команду |
| `local` | Переменная, видимая только внутри функции |
| `shellcheck` | Программа, которая находит типичные ошибки в скриптах |

## Вопросы с собеседований

Раздел для повторения: ответь вслух, потом открой ответ. Вопросы с пометкой `[на скорость]` тренируй на время: ответ за 30 секунд.

### 1. [junior] [часто] Что такое код возврата и как его проверить?

<details markdown="1">
<summary>Ответ</summary>

Число, которое программа отдаёт при завершении: 0 значит успех, любое другое значение ошибку. Проверяют специальной переменной `$?` сразу после команды или условием `if команда; then`. Свой скрипт завершают командой `exit N`.

**Что хотят услышать:** ноль это успех, `$?`, `exit`.

**Красный флаг:** «ноль значит ошибку» (путает с другими языками).

</details>

### 2. [junior] [часто] Чем одинарные кавычки отличаются от двойных в Bash?

<details markdown="1">
<summary>Ответ</summary>

Двойные подставляют значения переменных и команд (`"$HOST"`, `"$(date)"`), одинарные печатают текст буквально. Переменные в аргументах почти всегда берут в двойные кавычки, чтобы значение с пробелами не развалилось на несколько слов.

**Что хотят услышать:** подстановка против буквального текста, защита от пробелов.

**Красный флаг:** считает, что разницы нет.

</details>

### 3. [junior] [часто] Как сделать скрипт исполняемым и запустить?

<details markdown="1">
<summary>Ответ</summary>

Первой строкой шебанг `#!/usr/bin/env bash`, затем `chmod +x script.sh` и запуск `./script.sh`. Либо без права исполнения: `bash script.sh`.

**Что хотят услышать:** шебанг, `chmod +x`, `./`.

**Красный флаг:** `script.sh` без `./` и удивление, что «команда не найдена».

</details>

### 4. [junior] Как в Bash сравнить числа и строки?

<details markdown="1">
<summary>Ответ</summary>

Строки: `[ "$a" = "$b" ]`, `!=`. Числа: `-eq`, `-ne`, `-gt`, `-lt`, `-ge`, `-le`, например `[ "$ms" -gt 500 ]`. Знаки `>` и `<` внутри `[ ]` не сравнивают числа, а перенаправляют вывод в файл. Внутри `[ ]` пробелы обязательны.

**Что хотят услышать:** два набора операторов, ловушка с `>`.

**Красный флаг:** `[ $ms > 500 ]`.

</details>

### 5. [junior] Как передать скрипту параметры и задать значения по умолчанию?

<details markdown="1">
<summary>Ответ</summary>

Через позиционные аргументы `$1`, `$2`. Значение по умолчанию: `HOST="${1:-127.0.0.1}"`: берёт `$1`, а если он пустой, подставляет второе значение.

**Что хотят услышать:** `$1`, `${1:-...}`.

**Красный флаг:** жёстко прописывает адрес в десяти местах.

</details>

### 6. [junior] Что делают `&&` и `||`?

<details markdown="1">
<summary>Ответ</summary>

`a && b` выполняет `b`, только если `a` завершилась успешно (код 0). `a || b` выполняет `b`, только если `a` провалилась. Например, `mkdir d && cd d` или `curl -sf URL || echo "не отвечает"`.

**Что хотят услышать:** зависимость от кода возврата.

**Красный флаг:** путает с логическими операторами других языков в условиях `if`.

</details>

### 7. [junior] Почему `curl` в скрипте может вернуть код 0, хотя сервис ответил ошибкой?

<details markdown="1">
<summary>Ответ</summary>

По умолчанию `curl` считает успехом сам факт получения ответа, даже 404 или 500. Чтобы код выхода отражал ошибки приложения, нужен `-f` (`--fail`) или явное сравнение `%{http_code}` с ожидаемым. Также нужен `--max-time`, чтобы скрипт не зависал.

**Что хотят услышать:** `-f`, или `-w '%{http_code}'`, и таймаут.

**Красный флаг:** `if curl URL` без дополнительных проверок.

</details>

### 8. [middle] Как скрипту подождать, пока сервис поднимется, но не зависнуть навсегда?

<details markdown="1">
<summary>Ответ</summary>

Цикл с ограниченным числом попыток и паузой: `for i in {1..30}; do curl -sf URL > /dev/null && break; sleep 1; done`, после цикла проверить результат ещё раз и выйти с ненулевым кодом, если сервис так и не поднялся. Бесконечный цикл без предела опасен.

**Что хотят услышать:** предел попыток, пауза, проверка итога.

**Красный флаг:** `while true` без выхода и без `sleep`.

</details>

### 9. [middle] Зачем нужна `local` в функциях и что бывает без неё?

<details markdown="1">
<summary>Ответ</summary>

Без `local` переменная внутри функции становится общей на весь скрипт, и функции могут случайно затирать значения друг друга и основного кода. `local` ограничивает переменную функцией. Общими намеренно оставляют только то, что нужно передать наружу, например счётчик сбоев.

**Что хотят услышать:** видимость переменных, пример случайной перезаписи.

**Красный флаг:** все переменные глобальные.

</details>

### 10. [middle] Чем опасен скрипт без проверки ошибок и что делает `set -e`?

<details markdown="1">
<summary>Ответ</summary>

Bash по умолчанию продолжает работу после упавшей команды, и скрипт может завершиться с кодом 0, хотя в середине всё сломалось. `set -e` останавливает скрипт при первой ошибке, `set -u` ругается на необъявленные переменные, `set -o pipefail` считает ошибкой конвейера ошибку любой его команды. Вместе: `set -euo pipefail`. Для проверочных скриптов, которые должны собрать все сбои, вместо этого считают ошибки вручную и возвращают итоговый код.

**Что хотят услышать:** поведение по умолчанию, `set -e`, осознанный выбор между режимами.

**Красный флаг:** «скрипт же запустился, значит работает».

</details>

### 11. [junior] [на скорость] Как посмотреть код возврата последней команды?

<details markdown="1">
<summary>Ответ</summary>

`echo $?`.

**Что хотят услышать:** `$?`, и что он перезаписывается каждой командой.

**Красный флаг:** не знает.

</details>

### 12. [junior] [на скорость] Как записать вывод команды в переменную?

<details markdown="1">
<summary>Ответ</summary>

`VAR=$(команда)`.

**Что хотят услышать:** `$(...)` без пробелов вокруг `=`.

**Красный флаг:** `VAR = $(...)` с пробелами.

</details>

### 13. [junior] [на скорость] Какой код возврата означает успех?

<details markdown="1">
<summary>Ответ</summary>

Ноль.

**Что хотят услышать:** «0, всё остальное ошибка».

**Красный флаг:** «единица».

</details>

### 14. [junior] [на скорость] Чем отличается `./script.sh` от `bash script.sh`?

<details markdown="1">
<summary>Ответ</summary>

`./script.sh` запускает файл как программу: нужны шебанг и право исполнения. `bash script.sh` явно просит Bash прочитать файл, права исполнения не нужны.

**Что хотят услышать:** право исполнения и шебанг.

**Красный флаг:** считает их одним и тем же.

</details>
